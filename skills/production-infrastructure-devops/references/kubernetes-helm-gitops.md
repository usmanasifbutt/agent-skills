# Kubernetes, Helm, Helmfile & GitOps (ArgoCD)

## Helm — per-service charts, thin values, no umbrella chart

- **One versioned chart per service type**, pulled from a registry by **pinned semver**
  (`version: 0.6.8`, never `latest`). **No umbrella/parent chart** aggregating services — each
  service is an independent release; aggregation happens one level up in Helmfile.
- The deployment repo stores **only inputs** to charts (a `config.yaml` of values), never chart
  templates.
- **Why:** decoupling chart lifecycle (owned/tested/versioned centrally) from deployment config
  (owned per-environment) lets a chart be upgraded once and rolled out selectively; thin declarative
  values stay reviewable.
- **Tradeoff:** more charts to version-bump; value-schema drift between chart versions must be
  managed.
- **Common mistake:** a giant umbrella chart or a multi-thousand-line values file so one service's
  change re-renders everything; floating chart versions so a re-sync silently pulls a breaking chart.

## Helmfile — define once, render many

`helmfile.yaml` is a trivial entry point composing bases (repositories, environments, defaults) and
globbing `releases/*`. Each release is a **generic template** that loops over the services declared
in the active environment; a shared `templates/service` template computes the final, fully-defaulted
object. **A service is defined once and rendered per environment** by swapping environment values.

- **Why:** DRY at scale — upgrading a chart for all instances, enabling a feature everywhere, or
  changing a registry is a one-line edit; environments contribute only differences.
- **Tradeoff:** heavy Go-template logic is powerful but hard to debug (opaque template errors).
- **Common mistake:** copy-pasting a full release per environment instead of one template + per-env
  values; putting environment-specific literals inside the shared template.

### Three-tier value inheritance
Effective config is a merge of: (1) **defaults for all services**, (2) **defaults per
service-type**, (3) **per-service overrides**. Environments are auto-discovered (scan
`environments/*/`, inject `environmentDefaults`, then layer each file alphabetically). Cluster-level
fields (account, region, role, base domain) live in the environment; derived values come from
templates.

- **Tradeoff:** the "effective value" isn't visible in one place — you must mentally execute the
  merge chain.
- **Common mistake:** duplicating a value at all three tiers so overrides silently do nothing.

### Guardrails
- A **booby-trapped `default` environment** whose values are just `{{ fail "The default environment
  should not be used." }}` — since the CLI defaults `--environment` to `default`, any command
  missing an explicit environment fails loudly instead of deploying somewhere unintended.
- **JSON-schema validation of values in CI** (`schemas/`, draft 2020-12): per-environment,
  per-service, and per-chart-type schemas with `enum` allow-lists, `additionalProperties:false`,
  and `required` fields. Typos fail in PR review, not in-cluster.
- **Common mistake:** adding a config key without updating the schema (blocked in CI is *good*);
  leaving `additionalProperties` open so typo'd keys pass silently.

## Environment separation

Environments are `<tenant>-<env>` (staging / pre-prod / prod per tenant/region) plus special ones
(a shared review-apps env, a "global" env). **Each is a distinct cluster in a distinct account.**
Differences are pure values: chart versions, replica counts, resource requests/limits, autoscaler
bounds, worker formations, maintenance mode. Non-prod can pin different chart versions to test
upgrades first.

- **Common mistake:** letting staging and prod diverge *structurally* (different keys) rather than
  differing only in values; testing a chart bump in one tenant's staging and assuming it's safe for
  all.

## Review apps / ephemeral PR environments

Generated by ArgoCD **ApplicationSet Pull-Request generators** (one per tenant). For each labeled
PR, an Application `<tenant>-<pr>` spins up in its own namespace at its own URL, sourced from a
**throwaway branch** that only touches that review app's files (never merged). Config splits
**build-time (encrypted) vs runtime (plain)** so editing a test toggle doesn't trigger a rebuild.
**Cost control:** review apps auto-scale to 0 off-hours/weekends. Sync options are aggressive
(`Replace=true`, `selfHeal`, `PrunePropagationPolicy=foreground`, `revisionHistoryLimit:0`).

- **Common mistake:** making changes on the review-app branch that belong on the main branch (lost
  when the branch dies); build-time secrets in the plain runtime file; forgetting the sleep opt-out
  and burning cost.

## GitOps with ArgoCD

- **Pull model:** ArgoCD watches git; a merge triggers auto-sync. **Nothing is pushed from CI to the
  cluster** (no cluster credentials in CI).
- **App-of-apps bootstrap:** ArgoCD is installed via Kustomize (pinned upstream + local patches),
  then a root Application points at itself and an `application-sets` Application — ArgoCD manages
  ArgoCD.
- **Applications vs ApplicationSets vs Projects:** Applications (one per service) declare *how to
  render* (e.g. a config-management plugin runs Helmfile on demand) rather than embedding manifests;
  ApplicationSets fan out (review-app PR generators, per-cluster sets); Projects scope permissions
  (whitelist source repos + destinations).
- **Sync policy:** `automated` with `prune:true`, `CreateNamespace=true`, retry with exponential
  backoff; `selfHeal` where drift must be corrected.
- **`ignoreDifferences` on `Deployment.spec.replicas`** for autoscaled workloads — the canonical fix
  for the GitOps-vs-HPA conflict.
- **`manifest-generate-paths`** scoped to exactly the files that affect an app's render, so a commit
  only re-renders the relevant apps.

```yaml
syncPolicy:
  automated: { prune: true }
  syncOptions: [ CreateNamespace=true ]
  retry: { limit: 0, backoff: { duration: 5s, factor: 2, maxDuration: 3m } }
ignoreDifferences:
  - group: apps
    kind: Deployment
    jsonPointers: [ /spec/replicas ]   # let the autoscaler own replica count
```

- **Why:** git is the single source of truth; the pull model means no cluster creds in CI and
  continuous drift correction.
- **Tradeoff:** render-at-sync-time via a plugin is powerful but non-standard (slower renders, hence
  the path-scoping optimization); `prune` can delete resources if a file is mistakenly removed.
- **Common mistake:** auto-sync + prune while managing `replicas` in git for an autoscaled workload;
  not scoping `manifest-generate-paths` so every commit re-renders everything.

## Ingress, ALB groups & TLS

- Ingress via the **AWS Load Balancer Controller** using `alb.ingress.kubernetes.io/*` annotations.
  Multiple services share one ALB through an **ALB group name** (first service provisions it, others
  attach) — consolidates load balancers (cost + fewer public endpoints).
- **Traffic "formations":** one hostname routes by path/host/header to distinct deployments
  (e.g. `external` / `authenticated` / `read` / `tooling`), each independently replica-scaled and
  resourced — workload isolation rather than canary.
- **TLS** terminated at the ALB with an **ACM certificate** (referenced by ARN); `tls.hosts` may
  include wildcards. (In this estate TLS is ACM-at-the-ALB, not in-cluster cert-manager — though
  cert-manager is the standard alternative for in-cluster issuance.)
- **Common mistake:** an ALB per service (cost/sprawl) instead of a shared group; overlapping/
  misordered path rules so the wrong deployment serves a route; letting an ACM cert lapse.

## Rollout & rollback

- **Rollout = a git operation on an image tag.** A `config.yaml` carries `tag: <version>-<sha>`;
  bumping and merging it triggers ArgoCD auto-sync to roll the new image. Releases are `atomic:true`
  + `cleanupOnFail:true` with a Helm `timeout`, so a failed install rolls the *release* back
  automatically. Rollout is gated on ArgoCD/Helm health.
- **Rollback = `git revert`** the tag bump (or repoint `targetRevision`); ArgoCD re-syncs to the
  prior declared state. **Git history is the deployment history.**
- **Tradeoff:** rollback speed is bounded by re-render + re-sync; `git revert` does **not** undo
  external side effects (data migrations).
- **Common mistake:** promoting by re-pushing the *same* image tag (defeats auditability, ArgoCD
  sees no change); relying on `git revert` alone for changes with irreversible data-migration side
  effects; `kubectl rollout undo` on a cluster ArgoCD immediately re-syncs.
